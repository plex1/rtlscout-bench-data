# Session Summary

## Final outcome

Unfortunately, **my last submitted design (`design.sv`) did not pass** — the session ended with my rewrite still failing the equivalence check (1000 errors at file#221, opcode `0x18` = ALU_ADD in 8-bit vector mode). The only **PASS**ing design in the workspace remains `starting_point.sv` at **645,629 area_delay_product** (delay 1462 ps, area 441 µm²), which is the baseline I was never able to beat within the step budget.

## What I tried

**Diagnostic baseline first.** I ran `starting_point.sv` at `target_delay` = 500 ps and 2000 ps. The upstream ALU has a *very* long critical path (~1460 ps) because its result mux is a giant `unique case` driven by deeply factored shared datapaths (adder → round → shifter → minmax → clip → mux). Notably, at 2000 ps Yosys produced a *larger* delay (1627 ps) and only marginally smaller area, so area_delay_product got worse — a useful data point: this design is delay-dominated, and `target_delay` is a weak lever here.

**Full restructure of `design.sv`.** I rewrote the ALU with the intent of shortening the path:
- Byte-sliced adder (4× 9-bit lanes with an explicit carry chain, mode-selected carries) instead of the upstream 36-bit expanded adder.
- Fully logarithmic 5-stage barrel shifter using a reversed-operand-left / right-shift-plus-reverse trick, with per-lane arithmetic-fill for 32/16/8-bit modes.
- Shared 8-bit comparator per lane with sign-bit XOR for signedness, then a small prefix network for the 32/16-bit combines.
- Tree priority encoder for FF1 with OR-reduction levels, shared with FL1/CLB/div-shift.
- Verbatim upstream serial divider (cycle behaviour must match exactly).

## What worked

The **restructured shifter, comparator, popcount and FF1** all validated: the design progressed from 0 → 125,868 → 126,691 → 414,444 passing checks across iterations. Lint was clean. The modular structure (separate `sh_st[]` stages, `gen_byte_add`, `gen_cmp`) was much easier to debug than the flat upstream code.

## What didn't work / caused regressions

1. **SystemVerilog replication syntax** — `{2{a}, 2{b}}` is illegal; needs `{{2{a}}, {2{b}}}`. Cost one iteration.
2. **`PROCASSWIRE`** — Verilator rejects `wire` declarations for signals assigned inside `always_comb`. Signals like `reg_sel`, `cmp_result`, `ff_input`, `bitop_result`, `reverse_result` must be `logic`. Cost two iterations.
3. **Priority-encoder tree indexing** — I initially wired the FF1 mux levels with indices `l3[2]`, `l2[2]/l2[4]/l2[6]`, `l1[2]...l1[14]`, which is wrong: each level must use *consecutive* indices (`l3[1]`, `l2[1..3]`, `l1[1..7]`). This broke every div/rem (wrong `div_shift`) and every bit-count op.
4. **`ALU_SHUF2` label appearing twice** in one `unique case` — Verilator aborts with "multiple matches". Had to merge the two arms into one.
5. **CLIP semantics** — this was the hardest to reverse-engineer. The reference does *not* implement a clean `clamp(a, ~b, b)`. It reuses the byte-partitioned adder with `adder_in_b[0]=1` and takes the sign of the **top 9-bit lane** (`adder_result_expanded[36]`). It only coincidentally matches a signed compare because in 32-bit mode the byte carries chain together. My first attempt (`operand_a_i[31] | operand_b_i[31]`) was wrong; the correct form is `c[3]` where `c[3]` is the carry out of the top byte adder. Also `is_equal_clip` compares against `operand_b_neg` (CLIP) or `0` (CLIPU), and CLIPU's signed compare needs `cmp_sgn |= is_clipu` because `CLIPU` = `7'b0010111` has `operator_i[0]=1`, which my `~operator_i[0]` signedness heuristic read as *unsigned*.
6. **The vector-mode carry chain** — my final open bug. For `VEC_MODE8` with `neg_mode=0` (plain ADD in 8-bit lanes) the per-lane carry-in must be **0**, and for `VEC_MODE8` with `neg_mode=1` it must be **1**. I wrote `e[j] = vm8 ? neg_mode : ...`, which is correct, but the remaining errors (`ff7f80fe + 0000007f` → byte 1 expected `0x80`, got `0x81`) show that lane 1 of the *reference* still receives a carry from lane 0 in some configuration — i.e. the true upstream model is `adder_in_a[9] = 0` in add-mode but `adder_in_b[9] = 1` in negate-mode, and these are **not** symmetric in the way my `e[]` expression assumed. The correct expression needs to distinguish `add_a`'s forced-zero slot from `add_b`'s forced-carry slot separately (exactly as upstream does with two independent `case (vector_mode_i)` blocks on `adder_in_a` and `adder_in_b`).

## Lessons learned / what to do differently

- **Read the reference datapath structurally, not semantically.** The upstream ALU's "logical" spec (e.g. "clamp(a, ~b, b)") diverges from the RTL in edge cases because the RTL reuses one physical adder with per-byte carry partitioning. Reverse-engineering the *carry slots* (`adder_in_a[0,9,18,27]` and `adder_in_b[0,9,18,27]`) as eight independent 2-way muxes would have been far faster than guessing closed-form expressions. **Copy the two `case (vector_mode_i)` blocks verbatim**, then let Yosys collapse them — the RTL text need not be "elegant" to synthesize well.
- **Fix correctness in the smallest possible delta.** I burned ~15 steps on lint/syntax churn from a full rewrite. A better plan: take `starting_point.sv`, apply *one* structural change at a time (e.g. only the shifter), evaluate, keep or revert. That gives a monotone-improving history instead of a long red streak.
- **Preserve a known-good checkpoint.** I should have copied `starting_point.sv` to `design_v0.sv` first and kept `design.sv` as the always-passing submission, developing experiments in `design_x1.sv` etc. As it stands, the workspace's best passing file is still the untouched `starting_point.sv`.
- **Priority for a future agent:** the dominant delay is the result-mux / shared-datapath serialization. A high-value, low-risk optimization is to **duplicate** the comparator and min/max logic so that `comparison_result_o` and `result_o` for the 14 comparison opcodes don't route through the shifter, and to give the adder family its own short mux path. The area cost of duplication is small compared to the delay saving, and it does not change any arithmetic semantics — much safer than rewriting the adder's carry model.
- Keep `target_delay` around 400–600 ps for this design; 2000 ps made both metrics worse.
